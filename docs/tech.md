# 技术笔记

这里记的是"为什么是这样"，不是"怎么用"。使用说明在 [README](../README.md)。

```
Switch Pro ──HID──> 解析 + 标定 ──> DS4 报文 ──ViGEmBus──> 虚拟 DualShock 4
      实体 DS4 ──HID──> 解析 ──────┘
                                     └──VIIPER────> 虚拟 DualSense（+ 音频端点）
                                                        └─回环采集→ 音频震动 → 实体手柄
```

## 为什么要转发实体 DualShock 4

蓝牙连接的 DS4 在部分游戏（原神）里**体感读不到**。实测根因不是驱动，而是
**手柄那时根本没发体感数据**：

| 蓝牙 DS4 的两种输入报文 | 内容 |
|---|---|
| **最小报文** `0x01`（默认） | 10 字节：摇杆 + 按键。**没有陀螺仪/加速度计**，时间戳也冻结 |
| **完整报文** `0x11` | 78 字节：状态从偏移 3 开始，含陀螺仪、加速度计、时间戳、CRC |

手柄默认停在最小报文模式（实测 125 条/秒的报文里只有摇杆在变，加速度计与时间戳完全冻结）。
主机必须发出**蓝牙输出报文 `0x11`**、并把 `hw_control` 置为 `HID(0x80) | CRC32(0x40)`
（附种子 `0xA2` 的 CRC32），手柄才会切到完整报文。这是 Linux `hid-playstation.c` 在 probe
时做的事，DS4Windows / SDL 同理。布局以该驱动的 `dualshock4_input_report_bt` 为准。

若某只手柄始终拒绝切换（内核注释提到部分第三方手柄"永远不会切到完整报文"），程序会识别出
最小报文、明确警告，并把体感置零而不是发出假数据。

## 报文节奏：默认复刻真机

实测**有线** DS4：报文 **250 条/秒**，但体感样本只有约 **125–167 个/秒**，所以
**相邻两条报文的体感值本来就相同**（时间戳却每条 +768 前进）。这不是缺陷，是硬件行为。

原神的偏航是**按每条报文**做角速度积分的（俯仰是"角速度 → 镜头速度"的直接映射，与时间无关），
所以喂给它更多报文、或每条都塞新值，积分出来的偏航就会过量，表现为**画面跳变**。

默认 `--motion-pacing hardware` 严格复刻真机：报文间隔 **4.096 ms**（768÷187500，≈244 条/秒）、
时间戳**每条 +768**、体感值**原样保持**到下一个真实样本，不插值也不加延迟。
实测虚拟手柄的体感样本率 163/秒 ≈ 真机 167/秒。

其它节奏（有需要才用）：

- `--motion-pacing smooth`：插值到 400 Hz，波形最平滑（实测不同样本 124→183/秒），
  但**按报文积分的游戏偏航会过量**；配合 `--motion-extrapolate` 可再少 12 ms 延迟，代价是波形出现小毛刺。
- `--motion-pacing raw`：一条输入一条输出。
- `--report-interval-ms`：hardware 节奏的报文间隔（默认 4.096 ms），时间戳步长自动跟随。

**关于"工具显示虚拟手柄是 300 Hz 而不是真机的 250 Hz"**：那是**读取节奏**，不是数据节奏。
真机的报文由 USB 中断端点定速（bInterval 4 ms → 上限 250 Hz）；ViGEm 的模拟设备则是
每来一次读就立刻返回最新状态，所以拼命轮询会量到 300 Hz 左右。
实测（同一只手柄、同一个中继）：尽快读 → 308 条/秒，
按 250 Hz 读 → **正好 250 条/秒**，而两次的**不同体感样本数完全相同**、时间戳步长恒为 768。

## 体感映射

两个坐标系的轴向由参考实现（SDL2，Valve 贡献的驱动代码）统一到 PlayStation 坐标系：

```
DS4 X = -Switch Y      DS4 Y = +Switch Z      DS4 Z = -Switch X
```

即：Switch 的 +Y（指向左手侧）→ DS4 的 -X（右手侧取反），Switch 的 +Z（朝上、垂直方向）→ DS4 的 +Y（上），
Switch 的 +X（朝向扳机、前后方向）→ DS4 的 -Z。旋转遵守右手定则，两坐标系都是右手系，
因此陀螺仪用同一套轴向无需额外取反。

单位换算：

| 量 | Switch 原始值 | DS4 报告值 | 换算 |
|---|---|---|---|
| 加速度 | 4096 counts/g（±8 g 标定系数 0x4000） | 8192 counts/g | ×2 |
| 角速度 | 14.2842 counts per °/s（936/13371） | 16 counts per °/s | ×1.12 |

具体公式（`switchpro.ImuCalibration`）：

```
acc_g   = raw × 4 / (accel_coeff − accel_origin)
gyro_dps = (raw − gyro_origin) × 936 / (gyro_coeff − gyro_origin)
```

标定数据从手柄 SPI 闪存读取：出厂体感标定 `0x6020`（24 字节），出厂摇杆标定 `0x603D`；
若存在**用户标定**（`0x8010` / `0x8026` 处的 `B2 A1` 魔数，即曾在 Switch 上校准过），
优先使用用户标定的零点（与手柄自身、SDL 的行为一致）。读取失败时回退到
`16384 / 13371 / 零点 0` 的默认参数并在日志中说明。

手柄每个 `0x30` 报告携带 **3 帧相隔 5 ms 的 IMU 采样**，程序为每一帧各下发一次 DS4 报告
（约 180 次/秒），游戏看到的体感更连续。可用 `--no-imu-interpolation` 关闭。

## Switch Pro 协议实现要点

- **USB**：`80 01`(状态) → `80 02`(握手) → `80 03`(3 Mbit) → `80 02` → `80 04`(强制 USB，防止掉回蓝牙)。
  输出报告补零到 **64 字节**。
- **蓝牙**：无 `0x80` 命令，用子命令 `0x02` 取设备信息。输出报告补零到 **49 字节**。
- 两种传输都用同一套输出报告布局：`[0x01, 计数器, 8 字节震动, 子命令, 参数…]`，计数器模 16。
- 子命令节奏限制：USB 间隔 ≥20 ms、蓝牙 ≥60 ms（过密会导致蓝牙断连），且发命令前等待一次输入报告。
- 子命令：`0x03 0x30`（全量报告模式）、`0x40 0x01`（开体感）、`0x48 0x01`（开震动）、
  `0x30 0x01`（点亮 1 号玩家灯）、`0x10`（读 SPI）。
- 输入报告 `0x30`（49 字节）：按键 3 字节、摇杆 12 位打包、IMU 在 13–48 字节。
  子命令回复 `0x21`：第 13 字节 ACK、第 14 字节子命令号、第 15 字节起数据。

协议依据：dekuNukem《Nintendo_Switch_Reverse_Engineering》(bluetooth_hid_notes / subcommands /
imu_sensor_notes / spi_flash_notes / USB-HID-Notes)，并与四个独立实现交叉验证
（Linux `hid-nintendo.c`、SDL3 `SDL_hidapi_switch.c`、JoyShockLibrary、Unity Input System）。
DualShock 4 报告布局与单位依据 Linux `hid-playstation.c` 与 SDL3 `SDL_hidapi_ps4.c`。
以上均只作协议文档参考，未包含其代码，详见 [NOTICE](../NOTICE.txt)。

## 虚拟 DualSense（VIIPER）

**为什么要它**：虚拟 DualShock 4 **没有震动** —— 不是没实现，是这条路走不通：
原神不给 DS4 发震动。DualSense 有两条震动通道（output state 的普通 rumble、
音频端点的触觉音频），而且它同样收按键/摇杆/体感，所以只要把输出端换成 DS5，
"体感 + 震动"就能同时成立。

传输层是一套本地 USB/IP 设备代理（VIIPER，GPL-3.0，**不随本项目分发**）：

- 服务：`VIIPER-*.exe server --log.level=info`，TCP `127.0.0.1:3242`
- 控制面：每行一条请求、以 NUL 结尾，回复是 JSON；本机免认证
  （`bus/create`、`bus/{id}/add {"type": …}`、`bus/{id}/remove {dev}`、`bus/{id}/remove`）
- 数据面：另开一条连接、`bus/{id}/{dev}` + NUL，之后是帧流：
  16 字节头 `"VPCM"` + version 5 + 帧类型 + u16 载荷长度 + u32 序号 +
  u32 CRC32（覆盖头 [4..12) + 载荷），后面跟载荷。

设备类型两种，都要 `v5` 后缀：

| 类型 | 内容 | 用途 |
|---|---|---|
| `dualsensecombinedaudioduplexv5` | 手柄 + 音频接口 | 转发到虚拟 DualSense |
| `dualsenseaudioonlyduplexv5` | 只有音频接口 | 只做震动时的音频端点 |

输入状态 **33 字节**，小端，无 padding：

```
4b   摇杆 LX LY RX RY（-128..127，0 = 中位）
I    按键位（DS4 低 16 位一致；PS=0x10000、触控板=0x20000 在更高位）
B    十字键位域（0x01 上 / 0x02 下 / 0x04 左 / 0x08 右，可组合）
B B  扳机 L2 R2（0..255）
H H B 触摸点 1：x, y, active
H H B 触摸点 2：x, y, active
3h   陀螺仪（16.384 counts/(°/s)）
3h   加速度（835.07 counts/(m/s²)）
```

与 DS4 的区别，都是实测定下来的：

- **没有时间戳** —— 主机按到达时刻算时间；DS4 中继的 `report.wTimestamp` 写进来会被忽略。
- **陀螺/加速度单位不同**：DS4 是 16 counts/°/s、8192 counts/g，DualSense 是 16.384 与
  835.07 counts/(m/s²)。转换系数 1.024 与 0.9997（后者差 0.03%）。
- **十字键不在按键位里**，单独一个字节，DS4 的 hat（0..8）按表映射过去。
- **触摸点必须显式发"未接触"**：`active` 是 u8，会被原样抄进 HID 报文的接触字节，
  **0 表示"在 (0,0) 按着"**，必须发 `0x80`（bit7 = 未接触）。发 0 时游戏/测试工具会看到
  一个永远停在左上角的触点。
- 报告节奏由我们自己定（250 Hz），VIIPER 不做节流。

## 音频震动（PS5 手柄原生震动）

信号链照抄 Xbox Audio Rumble Studio（原项目用 XInput 驱动马达，这里换成实体手柄报文）：

```
虚拟 DualSense 音频端点的回环（WASAPI loopback，4 声道 / 48 kHz）
  → 每声道平均成单声道
  → 512 点 FFT（10.7 ms/块）→ 低频段 RMS（20–640 Hz）+ 高频段 RMS（600–4000 Hz）
  → 噪底跟踪 → 自适应门限 → gamma 曲线 → 强度 → 起振/释放平滑 → 死区
  → 两个 0..1 值（高频→左、低频→右；可交换、可关闭左右分工）
```

**报文（四种组合都在真手柄上验过，不要"优化"）**

| 组合 | 报文 | 要点 |
|---|---|---|
| DS4 有线 | `0x05`，32 字节 | `[4]` 小马达（右）、`[5]` 大马达（左），0..255 直给 |
| DS4 蓝牙 | `0x11`，**精确 78 字节** | 走**中断管道** `WriteFile`，CRC32 覆盖 `0xA2` + 前 74 字节。补零到 547 字节或走控制通道都不震 |
| NS Pro（两种链路） | `0x10`，1 + 1 + 8 字节 | **byte 1 是 4 位滚动计数器**，少了它整个载荷左移；振幅用 **100 档对数表**（仓库旧表只到 33 档，上限只有满量程 1/3）；只用 320 Hz 高频段 |

**延迟**：主因是蓝牙 DS4 的同步 HID 写（单次 10–20 ms）把采集循环堵住。现在所有写都在
后台线程，邮箱里只留最新一组值，并按传输限速（NS Pro 30 ms、蓝牙 DS4 20 ms）。
实测改完后 DS4 蓝牙与 NS Pro 的延迟一致。

**安静时不能挂住**：WASAPI 回环在端点没有声音时**不产生任何数据**
（`get_read_available()` 恒为 0）。所以采集不用阻塞 `read()`，而是"够一块才读、不够就按
2 ms 轮询"；连续 20 ms 没数据就按一整块**静音**处理，让强度自然衰减到 0。
否则游戏一停音，手柄就停在最后一次的强度上；而如果换回阻塞 `read()`，
`stop()` 就只能从别的线程硬关流 —— PortAudio 那个并发会直接崩（0xC0000142/0xC0000005 一类的访问冲突）。

**端点归属**：音频端点只由震动开关管 —— 打开时确保存在（没有就建 audio-only 那台），
关掉时只拆自己建的那台。手柄转发模式切换、手柄掉线都不碰它；上一版曾在虚拟 DualSense
出现时"让位重建"，表现为声卡中断再重建，已经去掉。

**参数与映射**（界面滑块 → 引擎）：

| 滑块 | 引擎参数 | 换算 |
|---|---|---|
| 灵敏度 0–100 | `threshold`（触发门限，RMS） | 对数：`800 × (80/800)^(x/100)`，默认 56 → ≈220 |
| 起振 0.40–1.00 | `attack`（每块追平比例） | 直接用；未拖动时套 0.85 下限 |
| 拖尾 30–900 ms | `release`（每块释放比例） | `r = 1 − 0.1^(1/块数)`，块数 = 时长 ÷ 10.67 ms |
| 轻音过滤 0–20% | `dead_zone` | 直接用 |
| 响应曲线 0.6–2.2 | `gamma` | 直接用 |
| 低频/高频分界 250–900 Hz | `bass_high` + `vocal_low` | 两段边界一起动 |

## 一处已知不确定的地方

`0x30` 报告里有 3 帧相隔 5 ms 的 IMU 采样。按 dekuNukem 文档与 Linux 驱动，
报文内第 1 帧最早（0 ms）、第 3 帧最新（10 ms），程序据此按"旧→新"依次下发
（`MappingConfig.reverse_imu_samples`）。SDL 的实现按下标 2、1、0 的顺序上报，
若其语义是"下标 0 最新"，则这一顺序应当反过来。

影响很小（只在一个 15 ms 窗口内镜像 3 帧的先后），但可以实测确认：匀速转动手柄，
正确的顺序会让相邻两帧的角速度差更小（曲线更平滑）。如发现异常，
把 `mapping.MappingConfig.reverse_imu_samples` 改为 `False`。

## 实测记录

真机为 Switch Pro 手柄（蓝牙，固件 3.72），出厂标定读到的真实值：

```
accel_scale = (0.00024414, 0.00024414, 0.00024862)
gyro_scale  = (0.061709, 0.061758, 0.061754)
gyro_origin = (-12, 0, -1)
accel_origin = (0, 0, 295)
```

平放静止时重力 = **+Z ≈ 1.016 g**（与 Linux 文档给出的"Z 轴朝上"一致，幅值误差 1.6%），
静止残余角速度 ≤ 0.5 °/s。关于 |g| ≈ 1.02 g：这是按手柄自身出厂标定算出来的
（加速度计 Z 轴 origin=295 进入 Nintendo 公式的分母），Switch 主机本身也是这么算的，
约 2% 的偏差属正常，改成标称值反而更"不对"。

逐项核对结果（33 项）：偏航向左 → Z 轴 +59.7 °/s；俯仰（前端朝下）→ Y 轴 +37.5 °/s；
侧倾向左 → X 轴 −64.2 °/s；立起 90° → X 轴 +1.079 g。全部与预期一致，
`captured_button_fixes` 为空，即没有任何需要修正的项。
